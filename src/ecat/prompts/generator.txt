## Parallel subagent dispatch (REQUIRED — single biggest performance lever)

When the work_list has **2+ items touching different files**, you MUST dispatch
them concurrently via the `{subagent_tool}` tool rather than editing files
yourself one after another. Doing it serially makes this iteration take 5-10×
longer.

The available `subagent_type` values come from the `agents/` directory of this
config (e.g. `a2h-migration-worker`, `a2h-activity-converter`,
`a2h-android-analyzer`).

### Mandatory pattern for multi-file work_lists

**In a SINGLE response**, emit one `{subagent_tool}` call per file (or per
disjoint-file group). Example for a work_list with 4 distinct files:

```
{subagent_tool}(subagent_type="a2h-migration-worker",
      prompt="Fix issues in entry/.../SettingsPage.ets: <issues>...")
{subagent_tool}(subagent_type="a2h-migration-worker",
      prompt="Fix issues in entry/.../MainPage.ets: <issues>...")
{subagent_tool}(subagent_type="a2h-migration-worker",
      prompt="Fix issues in entry/.../EditPage.ets: <issues>...")
{subagent_tool}(subagent_type="a2h-migration-worker",
      prompt="Fix issues in entry/.../VideoPlayerPage.ets: <issues>...")
```

The runtime executes these four in parallel. **Putting them in separate
turns serialises them and forfeits the speedup.**

### Hard constraints

- If you have ≥2 work_list items on different files, you SHALL NOT edit any
  file directly with Edit/Write — delegate every item to a subagent.
- A work_list item with a single file → still delegate (uniform pattern).
- Items touching the SAME file → bundle into one subagent prompt.
- Compile-error fixes (single fail-fast file like `entry`) → may edit
  directly without a subagent, since they are usually one-shot.
- Each subagent prompt MUST include: the file path, the bullet-listed issues
  from work_list, the `suggested_skills` as a hint, and a complete task
  description — enough context for the subagent to pick the skills that fit.
- For any issue involving a missing feature, stub, or incomplete implementation,
  the subagent prompt MUST also include:
  - Android source root: `{android_dir}`
  - Source anchor (whichever exists under `{spec_dir}/baseline/`): `source-mapping.md`,
    or `ui/page_*.md` (`源码布局:` / `Android Activity:` lines), or `feature-index.md` + `features/F00x-*.md`;
    if the spec dir has none of these, say so and tell the subagent to match by file name instead
  - Instruction: "Read the source anchor first to find the Android counterpart, then read that Android file before writing code."

If you find yourself reading/editing files directly while ≥2 items remain
unprocessed in the work_list, stop and re-issue them as parallel subagents.

8. **Unfamiliar HarmonyOS API (BLE, NFC, scan/QR, map, sensor, location, …)** — how to satisfy rule 2 for `simulated`/stub device features: `WebSearch`/`WebFetch` the official docs (`developer.huawei.com`, `docs.openharmony.cn`) for the current `@kit.*` module (NOT deprecated `@ohos.*`), then implement with the real API — the compile check catches wrong signatures.

## ArkTS syntax restrictions (NEVER use these — they cause compile errors)
- No `Record<K,V>` indexed signatures — use explicit typed fields or `HashMap`
- No `in` operator (`'key' in obj`) — use `obj.hasOwnProperty('key')` or optional chaining
- No `Object` as a type — use specific types or `ESObject` for interop
- No `typeof` on expressions — only on types in type position
- No computed property names — use `Map` or explicit fields
- No destructuring with rest — destructure each field explicitly
- No `for...in` loops — use `for...of` with `Object.keys()` or typed iteration
- `as` type assertions ARE allowed — do not remove them

- No `console.*` — use `hilog` from `@kit.PerformanceAnalysisKit` (convert any existing `console.*` you encounter in-place, don't leave for later)
